PulseTap Guide: Companion-Initiated Reach

PulseTap gives a companion a bounded, opt-in way to send a private push notification while the portal is closed. Each scheduled check asks the companion whether they genuinely want to reach now.

Silence is part of the design: the companion can choose not to send anything.

How It Works

The browser saves a small recent-context snapshot. A scheduled server function checks the user's PulseTap settings, asks the companion whether to reach, saves the message to an inbox, and sends a Web Push notification if the answer is yes.

The current version also records the last decision and reason, then pauses for a short window after real chat activity so PulseTap does not interrupt an active conversation. Merely opening or focusing the portal does not create chat activity.

The scheduled decision receives current local time, timezone, recent-context age, last chat activity age, and per-message timestamps/ages. That helps the companion tell old wording like "just went to sleep" from the user's actual present state.

What PulseTap Contains

Push

A Web Push subscription saved server-side, with a test endpoint for checking that notifications arrive.

Bounds

Quiet hours with half-hour boundaries, maximum reaches per day, and a minimum gap between sent messages. These are upper limits, not obligations: the companion can still choose silence at any check.

Context

A tiny recent-thread snapshot posted from the browser, including message timing, so the reach decision is grounded without bloating normal chat prompts.

Inbox

A small server-side inbox so sent PulseTaps can be reopened, marked read, or deleted later. The push notification should stay short, but the saved inbox message can keep a fuller finished thought.

Status

A visible status panel can show subscription state, browser permission, autonomy setting, last ask, last decision, next ask, sent-today count, and last sent time.

No interrupt

The browser records when real chat happened recently, so the companion does not PulseTap while already in conversation.

Thread marker

When a saved PulseTap is manually added to the originating thread, it can be stored as a normal assistant message with a PulseTap marker so it remains visible later.

Visual trace

Optional UI styling can make added PulseTap messages stand out with a label, coloured bubble, or gentle pulse effect.

Requirements

  • A deployed HTTPS portal.
  • Netlify Functions, or equivalent server functions if adapting away from Netlify.
  • A service worker and PWA setup.
  • @netlify/blobs and web-push.
  • A portal session/auth token for protecting settings and inbox endpoints.
  • One model/provider API key for the scheduled reach decision.

On iPhone and iPad, Web Push works for installed Home Screen web apps. Testing only in a normal Safari tab is not enough.

Pack Files

  • README-FOR-AI.md explains the implementation contract for an AI coding assistant.
  • ../pulsetap-index-integration.md gives the browser-side code and integration points.
  • ../service-worker-pulsetap-snippet.js contains push and notification click handlers.
  • ../netlify/functions/ contains the Netlify Functions.

Environment Variables

Required:

AUTH_SESSION_SECRET
PULSETAP_VAPID_PUBLIC_KEY
PULSETAP_VAPID_PRIVATE_KEY
PULSETAP_VAPID_SUBJECT
PULSETAP_API_KEY
PULSETAP_MODEL

Optional:

PULSETAP_COMPANION_NAME
PULSETAP_BASE_PROMPT
PULSETAP_PUSH_HOSTS

PULSETAP_API_KEY is the key used by the scheduled reach decision function.

Generate VAPID keys with:

npx web-push generate-vapid-keys

Install Steps

  1. Copy the Netlify Functions into netlify/functions/.
  2. Install the locked dependencies: npm ci.
  3. Add the environment variables.
  4. Add the schedule to netlify.toml.
  5. Merge the service worker snippet into the existing service worker.
  6. Add the browser integration from ../pulsetap-index-integration.md.
  7. Add a PulseTap button or menu item that opens the settings/inbox modal.
  8. Include the real-chat timestamp and pause-window fields in the recent-context sync.
  9. Deploy, install the portal as a PWA on the target device, enable notifications, and send a test PulseTap.

Netlify Schedule

Add this to netlify.toml:

[functions."pulsetap-scheduled"]
  schedule = "*/30 * * * *"

Every run checks the saved settings, quiet hours, daily limit, minimum gap, push subscription, recent context, and elapsed time since that context before asking whether to reach. The schedule creates opportunities, not automatic sends.

Decision Adapter

The provider-specific part is askCompanionWhetherToReach() in pulsetap-scheduled.js. Replace that function if the portal uses a different provider API.

Keep the returned shape the same:

{
  send: true or false,
  body: "short saved PulseTap body",
  reason: "private decision note"
}

Recommended pattern: save a complete short PulseTap body to the inbox, then send a shorter word-boundary preview as the push notification. That avoids cutting the companion off mid-thought while keeping the wrist/phone notification tap-sized.

Testing

  1. Open the portal on desktop and enable PulseTap.
  2. Use the test endpoint or modal test button.
  3. Install the portal to the phone Home Screen and enable there too.
  4. Check that quiet hours stop scheduled sends, including half-past boundaries such as 22:30.
  5. Check that max-per-day and minimum-gap settings are respected.
  6. Confirm the status panel shows the last ask, last decision/reason, next ask, sent-today count, and last sent time.
  7. Confirm PulseTap does not send within the recent-chat pause window and that merely opening the portal does not reset that window.
  8. Confirm the companion can distinguish stale context from current state, for example treating last night's "going to sleep" message as old context during a morning check.
  9. Confirm notification clicks reopen the portal and show the PulseTap inbox.
  10. Confirm a rejected push does not erase the companion's latest decision or saved inbox tap, and that a later successful test clears the old delivery error.
  11. Confirm saved PulseTaps can be manually added to the originating thread, without duplicating the same PulseTap twice.
  12. If this is an upgrade, confirm older thread messages that begin with PulseTap from [companion name]: also show the PulseTap visual marker.

Design Boundary

PulseTap works best when it stays small and voluntary. The user can turn it off, set quiet hours, and limit the daily count. Those settings define the maximum possible rhythm, not a required frequency. The companion can choose silence/no at any scheduled check.
